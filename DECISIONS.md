# Decisions

Key design decisions in picklescope, each with the reasoning and what it would cost if it turned out wrong.

- Write an independent opcode table and disassembler instead of wrapping `pickletools.genops` — the scanner needs structured, offset-carrying errors, resource limits and a guarantee that no stdlib helper ever calls into the unpickler; `pickletools` is used only as a test oracle (property tests on generated pickles) — cost if wrong: ~300 extra lines to maintain when a protocol 6 appears.
- Abstract interpretation of the stack machine rather than "grep GLOBAL opcodes" — memo indirection, computed `STACK_GLOBAL` operands, indirect calls and global mutation are invisible to a flat opcode scan, and they are exactly the evasions used against existing scanners — cost if wrong: more code than a pattern scan; mitigated by 99% branch-level coverage of the analyser.
- Mirror CPython's C unpickler mark semantics (fences, `POP` discards an empty frame) — stack alignment must match a real load or later imports are attributed to the wrong values — cost if wrong: a crafted stream that the pure-Python unpickler accepts but the C one rejects could be mis-modelled; the C implementation is what `pickle.load` uses.
- Allow-list first, deny-list only as a severity backstop; unknown imports are MEDIUM, unknown *invoked* imports HIGH, deny-listed imports CRITICAL even when not invoked — closed-world policy is the only defensible model for an open-ended gadget space — cost if wrong: unusual-but-benign pickles (custom classes) produce medium/high findings and need a policy file.
- Policy precedence user deny > user allow > built-in deny > built-in allow — organisations must be able to override built-ins in both directions, with reasons recorded in their file — cost if wrong: a careless user allow can re-enable a deny-listed callable; reasons are shown in `policy check` output to make that visible.
- `sklearn` profile is opt-in and whole-package — estimator pickles reference hundreds of classes, enumerating them is brittle, but enabling the whole package by default would weaken the default policy — cost if wrong: sklearn users must pass `--profile sklearn`.
- Classify both the written and the `_compat_pickle`-mapped spelling of protocol < 3 names, deny on either — `__builtin__.getattr` must not slip past a `builtins` deny entry — cost if wrong: none observed; a mapped-name allow is accepted only when the raw name is unknown.
- Report `allowed` imports in an inventory (`--show-imports`, JSON `imports`) rather than as INFO findings — a torch archive would otherwise produce a dozen noise findings per file and SARIF consumers would show them — cost if wrong: users wanting INFO-level SARIF entries for allowed imports must read the JSON output.
- Never decompress `torch.save` storage records (`<prefix>/data/*`) and only sniff 16 bytes of other unknown members — weights can be gigabytes and cannot carry code in the torch format — cost if wrong: a payload hidden in a storage record is not scanned (a loader would also never unpickle it).
- Strongly-typed extensions (`.safetensors`, `.gguf`, `.npy`, `.onnx`) route undetectable content to their validator instead of "unknown format" — the validator explains precisely what is broken (e.g. header length past EOF) — cost if wrong: a random file named `.gguf` gets a `GG400` instead of a format-mismatch finding.
- Polyglot detection (`GEN903`) uses `zipfile.is_zipfile` on non-zip files — a pickle or safetensors file with a zip central directory appended is read differently by `torch.load` (magic at offset 0) and zip-based tools — cost if wrong: rare false positives on non-zip files that happen to end with an end-of-central-directory record.
- ONNX is decoded from the protobuf wire format with a ~100-line decoder instead of depending on `onnx` — keeps the runtime dependency-free and lets the walker bound depth and avoid copies; `onnx` is a dev dependency used for parity tests — cost if wrong: schema evolution (new fields that carry tensors) must be added by hand.
- For ONNX external data on disk, resolve with `Path.resolve()` and require containment before any `stat` — the scanner must not probe arbitrary host paths named by a hostile model — cost if wrong: resolution follows in-directory symlinks (a loop is reported as `OX502` "cannot be resolved"); a race where the directory changes between scan and load is out of scope.
- Keras HDF5 (`.h5`) support is a bounded byte search for the `model_config` JSON, not an HDF5 parser — writing an HDF5 reader is out of proportion and `h5py` would add a native dependency — cost if wrong: configs stored in fragmented HDF5 heaps are missed; documented as a heuristic.
- GGUF chat-template check is pattern-based (dunders, `|attr(`, `_TemplateReference__context`, process/exec calls) — the known Jinja SSTI payloads need one of these; rendering templates in a sandbox would mean executing attacker input — cost if wrong: novel SSTI without these constructs is missed; real templates checked (four public GGUF files) produced no false positives.
- The `.npy` header is parsed with `ast.literal_eval` after a 64 KiB cap — it is what NumPy itself does, evaluates literals only, and the cap bounds its cost — cost if wrong: none known; `MemoryError`/`RecursionError` are caught.
- Fixtures are assembled byte-by-byte by `tests/fixturegen.py`, committed (388 KiB), and regenerated in a test to prove they are in sync — reviewers can diff fixtures, and nothing is produced by pickling live objects — cost if wrong: generator and committed files can drift; the sync test fails loudly.
- Fixtures that must hit the CRITICAL path use harmless deny-listed names (`builtins.getattr` on `str`, `os.getcwd`) or a test policy that deny-lists `colorsys.rgb_to_hsv` — flagged fixtures must reference harmless callables only — cost if wrong: none; real dangerous names are covered by string-level policy unit tests.
- Real-model false-positive evaluation uses 14 small pinned files (torch zip, safetensors, ONNX, GGUF incl. Q4_0, Keras v3 archive and KerasHub preset configs, TF HDF5) fetched by commit hash + SHA-256 into `.cache/` and never committed — real models are the only honest false-positive check, and committed data is capped to keep the repo small — cost if wrong: 14 files is a small sample; the README reports it as such and adds a 2,000-sample random benign pickle corpus.
- SARIF byte regions only for top-level offsets; archive members go to `logicalLocations` — a member offset does not address bytes of the file on disk, and SARIF regions must — cost if wrong: GitHub code scanning shows member findings at file level rather than at a line.
- Severity thresholds: CLI exits 1 at `--fail-on medium` by default — medium is the lowest level that indicates something a reviewer must look at (unknown import, structural tampering) — cost if wrong: CI gates may be noisier than desired; configurable.
- Coverage gate 85% on the whole package (measured 98%) — contract asks for >= 80% on core logic; gating the whole package is stricter — cost if wrong: none.
- Scan every central-directory entry of a zip, duplicates included, and locate findings in the k-th copy of a repeated name at `name#k` — Python's `zipfile` resolves a name to its last entry while other readers (torch's miniz) may resolve another, so a scanner that reads one copy can be shown a benign pickle while the loader runs the other — cost if wrong: findings for identical duplicate copies are reported twice; `ZIP201` still flags the duplication itself.
- Treat a zip as Keras when its root `config.json` sits next to `metadata.json`, `model.weights.h5` or `model.weights.npz`, when the file is named `*.keras`, or when that `config.json` parses as a Keras object (string `class_name` plus `config`) — Keras 3 `saving_lib` deserializes `config.json` before it looks for any weights store, so marker files cannot be required; content-based promotion keeps the check working when the extension is changed — cost if wrong: a non-Keras zip whose root `config.json` happens to have `class_name` and `config` keys is walked as a Keras config and may report `KR603` for its `module` references; `config.json` in subdirectories is not promoted (Keras reads the root only).
